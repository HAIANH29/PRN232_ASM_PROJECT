# Physical Database

PostgreSQL is used with database-per-stateful-service ownership.

Local Docker Compose exposes the databases on separate host ports for development only:

- `IdentityDb`: `localhost:5433`
- `DietKnowledgeDb`: `localhost:5434`
- `MealPlanningDb`: `localhost:5435`
- `TrackingDb`: `localhost:5436`
- `VectorDb` (pgvector, owned by Diet Knowledge Service): `localhost:5437`

Uploaded PDF binaries are stored in a Docker/local file volume. PostgreSQL stores metadata, extracted chunks, and review candidates only.

## MealPlanningDb

- `MealPlans`
  - `Id`
  - `UserId`

  - `Name`
  - `StartDate`
  - `EndDate`
  - `CreatedAtUtc`
  - `UpdatedAtUtc`
- `MealPlanItems`
  - `Id`
  - `MealPlanId`
  - `PlannedDate`
  - `MealSlot`
  - `RecipeId`
  - `FoodId`
  - `Notes`
  - `ReminderAtUtc`
  - `CreatedAtUtc`
  - `UpdatedAtUtc`
- `MealRecommendationRequests`
  - `Id`
  - `UserId`
  - `PreferenceTagsJson`
  - `Days`
  - `Status`
  - `SuggestedMealTitlesJson`
  - `Disclaimer`
  - `AcceptedMealPlanId`
  - `RequestedAtUtc`
  - `CompletedAtUtc`
  - `UpdatedAtUtc`

- `OutboxMessages`
  - `Id`
  - `MessageType` (`ReminderRequested` or `RecommendationRequested`)
  - `PayloadJson`
  - `CreatedAtUtc`
  - `NextAttemptAtUtc`
  - `Attempts`, `LastError`
  - `ProcessedAtUtc` (null while the message still has to be published)

Owned by `Meal Planning Service`.

`OutboxMessages` implements the transactional outbox: reminder and recommendation messages are saved in the same transaction as the meal plan item or request that caused them. A background dispatcher then publishes them to RabbitMQ, retrying with a growing delay, so a broker outage never loses a message (delivery is at least once). Processed rows are deleted after one day. The Notification Worker asks Meal Planning (internal endpoint `GET /internal/reminders/{mealPlanItemId}`, shared key, not routed by the gateway) whether a delayed reminder still matches its item before sending it, so reminders for deleted or rescheduled meals are dropped.

`UserId`, `RecipeId`, and `FoodId` are cross-service identifiers only. They are indexed where useful but do not have cross-database foreign keys. `MealPlanItems` has an internal foreign key to `MealPlans` only.

Migrations exist: `InitialMealPlanningSchema`, `AddMealPlanDietRegimenId`, `AddOutboxMessages`.

`MealSchedule` is not represented as a separate table in the current workflow. The scheduling data is stored on `MealPlanItems` through `PlannedDate`, `MealSlot`, and `ReminderAtUtc`.

## VectorDb

Separate PostgreSQL container with the pgvector extension (`pgvector/pgvector:pg16`), `localhost:5437`. Owned by Diet Knowledge Service; no other service connects to it.

- `KnowledgeEmbeddings`
  - `Id`
  - `IndexRunId` (foreign key to `EmbeddingIndexRuns`)
  - `SourceType` (`Guideline`, `Food` or `Recipe`) and `SourceId`: bare ID of an approved item in DietKnowledgeDb, no foreign key (unique together)
  - `ContentHash` (SHA-256 of `Content`, used to skip unchanged items)
  - `Content` (title, category and approved text only, at most 4000 characters)
  - `Embedding` (`vector(768)`, HNSW index with cosine distance)
  - `EmbeddingModel` (for example `gemini:gemini-embedding-001:768` or `local-hash-768`)
  - `CreatedAtUtc`, `UpdatedAtUtc`
- `EmbeddingIndexRuns`
  - `Id`
  - `StartedAtUtc`, `CompletedAtUtc`
  - `ItemsIndexed`, `ItemsFailed`
  - `Status` (`Running`, `Completed`, `CompletedWithErrors`, `Failed`)

Migration: `InitialVectorSchema` (in `VectorDb/Migrations`). Only active `Approved` content is embedded; raw `BookSourceChunks` and unreviewed candidates never are. Rows whose source is no longer approved or active are removed on the next index run, but only when every item in that run embedded successfully.

## Revised design (lecturer feedback)

Diagram: `LongevityDiet-Database.drawio`. The lecturer's modules map as: 1 User (Identity), 2 Diet, 3 Diet Regimen (both in DietKnowledgeDb), 4 Meal Plan, 5 UserDietTracking, plus the separate VectorDb. Every table in the diagram is implemented in code and migrations: `UserProfiles`, `Categories` (with `CategoryId` on foods, recipes, guidelines), `NutritionFacts`, `RecipeSteps`, `DietRegimens`, `DietRegimenGuidelines`, `DietRegimenMeals`, `UserDietTrackings` (with `UserDietTrackingId` on daily tracking and progress summaries), `MealPlans.DietRegimenId`, and the VectorDb tables above.

`Foods` is the "Ingredient" entity of the lecturer's list; it keeps the name `Foods` in code and in the diagram ("Foods (Ingredient)").

## Verification Snapshot

- EF Core migrations exist for all four stateful service databases.
- Startup migration initializers apply migrations service-by-service.
- `dotnet test LongevityDietPlatform.sln` includes repository-level checks for Diet Knowledge search/filter/pagination and Tracking progress summary behavior.

## Rules

- No service reads another service database directly.
- No cross-database foreign keys.
- Do not create `RecommendationDb` or `NotificationDb` unless a future persistence requirement needs them.
- EF Core migrations exist for Identity, Diet Knowledge, Meal Planning, and Tracking.
- Uploaded PDF binaries are stored outside PostgreSQL in local/container storage; only metadata and extracted chunks are stored in DietKnowledgeDb.
